# new-api 缓存与配置生效排查 SOP

本文用于排查以下常见现象：

- 已发布，但前端页面还是旧内容
- 后台设置已保存，但线上行为没变
- 数据库里配置已更新，但接口返回仍是旧逻辑
- 新请求已生效，但历史页面展示仍是旧值

## 一、先判断是哪一类问题

不要把所有“没生效”都归因于缓存。先分类型：

### 1. 前端静态资源未刷新

典型表现：

- 页面文案、按钮、布局、开关位置还是旧的
- 换浏览器或无痕模式后恢复正常
- API 行为已经变了，但页面没变

### 2. 后端实例仍在跑旧代码

典型表现：

- 同一个接口，不同时间或不同请求返回不一致
- 数据库配置已是新值，但接口行为像旧版本
- 发布后部分请求命中新逻辑，部分还是旧逻辑

### 3. 数据库存的是历史结果，不会自动回填

典型表现：

- 新请求正常，旧日志/旧订单/旧任务仍显示旧值
- 页面展示的是历史落库字段，不是实时计算字段

### 4. 浏览器/CDN/边缘节点缓存

典型表现：

- 本地强刷后正常，普通刷新不正常
- 不同地区、不同网络访问结果不一致
- `curl` 请求正常，浏览器页面异常

## 二、项目里实际存在的缓存/状态层

这个项目至少有 5 层“看起来像缓存”的来源：

### 1. 浏览器缓存

- HTML
- JS chunk
- CSS
- 本地存储中的用户态配置

### 2. CDN / 边缘平台缓存

当前线上响应里常见：

- Cloudflare
- Vercel
- Zeabur

静态资源最容易被这些层缓存。

### 3. Go 进程内存配置

项目大量配置通过以下方式进入内存：

- `common.OptionMap`
- `setting/*`
- `operation_setting/*`
- `performance_setting/*`

数据库更新后，最终是否“立即生效”，取决于：

- 当前实例是否已重启
- 当前实例是否重新加载配置
- 是否存在多实例同时提供服务

### 4. 构建产物

前端每次构建都会生成新的 `dist/` 文件、SEO 产物、chunk 文件名。
如果发布流程没有完整替换产物，或者 CDN 还在给旧文件，就会出现“代码改了但页面像没改”。

### 5. 历史业务数据

以下内容很多是“写入即固化”，不是实时重算：

- `logs.other`
- `task.properties`
- 各类订单快照
- 站内消息、邮件内容快照

所以新逻辑不会自动修复旧数据。

## 三、标准排查顺序

按这个顺序查，最快。

### 第 1 步：先确认请求到底打到了哪个版本

先用 `curl` 直接打线上接口，不经过前端页面判断。

示例：

```bash
curl -i "https://fishxcode.com/v1/messages" \
  -H "content-type: application/json" \
  -H "anthropic-version: 2023-06-01" \
  -H "x-api-key: YOUR_KEY" \
  --data-raw '{"model":"claude-sonnet-4-6","max_tokens":16,"messages":[{"role":"user","content":"reply with ok only"}],"stream":false}'
```

重点看响应头：

- `x-oneapi-request-id`
- `cf-cache-status`
- `x-vercel-cache`
- `x-zeabur-request-id`

如果接口响应已经是新行为，问题通常不在后端逻辑，而在前端页面或历史数据。

### 第 2 步：拿 `request_id` 直接查数据库

不要只看页面展示，直接查库确认真实落库结果。

示例：

```sql
SELECT id, created_at, request_id, model_name, other
FROM logs
WHERE request_id = 'YOUR_REQUEST_ID'
ORDER BY id DESC
LIMIT 1;
```

判断方式：

- 数据库新记录是正确的：说明后端逻辑已生效
- 数据库新记录仍是旧值：说明旧代码仍在跑，或逻辑未真正发布

### 第 3 步：区分“新数据不对”还是“旧数据没迁移”

这是最容易误判的一步。

如果：

- 新请求正确
- 旧页面仍有旧数据

那不是缓存问题，而是历史数据没有回填。

这时应判断：

- 是否接受历史数据保留原样
- 是否需要单独写 SQL / 脚本迁移历史数据

### 第 4 步：确认前端是不是旧资源

如果 API 正常，但页面还不正常，优先怀疑前端资源。

排查动作：

1. 浏览器无痕窗口打开
2. DevTools 勾选 `Disable cache`
3. 强制刷新页面
4. 检查加载的 JS 文件名是否为新构建产物

如果无痕窗口正常、普通窗口异常，就是浏览器缓存问题。

### 第 5 步：确认平台是不是多实例/滚动发布未收敛

如果同一接口一会儿新一会儿旧，通常是：

- 旧实例未下线
- 新旧实例并存
- 平台滚动发布尚未完全收敛

这时应：

1. 连续发送多次相同请求
2. 对比返回头中的平台请求 ID
3. 对比数据库新写入记录是否稳定一致

如果结果不稳定，就是实例层问题，不是浏览器缓存。

## 四、针对 new-api 的专项判断

### 场景 1：后台设置保存了，但接口没变化

优先检查：

- `options` 表是否已更新
- `common.OptionMap` 对应 key 是否已同步到当前实例
- 相关开关是否只影响“展示”，不影响“真实处理链路”

典型误区：

- 以为改的是转发逻辑，实际上只改了日志展示逻辑
- 以为改的是实时字段，实际上页面读的是历史落库字段

### 场景 2：日志里旧值还在

先问自己两个问题：

1. 这是旧日志还是新日志？
2. 页面显示的是 `logs.other`，还是实时计算结果？

只要是旧日志，默认就不会自动变。

### 场景 3：模型漂移“好像还在”

以这次 `upstream_model_name` 为例，要拆成 3 件事：

1. 上游真实返回的模型是否漂移
2. API 响应体里的 `model` 是否仍显示上游模型
3. 日志里的 `other.upstream_model_name` 是否对用户做了收敛展示

这三件事可能只修了其中一件，不能混着判断。

## 五、最快排查命令清单

### 1. 看工作区是否真包含改动

```bash
git status --short
git diff --stat
```

### 2. 看线上接口是否命中新逻辑

```bash
curl -i "https://fishxcode.com/your/api"
```

### 3. 查数据库配置是否真写入

```sql
SELECT key, value
FROM options
WHERE key IN ('YOUR_OPTION_KEY');
```

### 4. 查请求日志是否按新逻辑落库

```sql
SELECT request_id, model_name, other
FROM logs
WHERE request_id = 'YOUR_REQUEST_ID';
```

### 5. 查是否存在多实例表现不一致

做同样请求 3 到 5 次，核对：

- 返回头请求 ID
- 数据库新日志
- 页面展示

## 六、处理策略

### 情况 A：前端缓存

处理方式：

- 强刷浏览器缓存
- 无痕验证
- 重新发布前端静态资源
- 必要时清理 CDN 缓存

### 情况 B：后端实例旧代码

处理方式：

- 确认发布是否成功
- 确认旧实例是否已下线
- 必要时重启服务

### 情况 C：历史数据未迁移

处理方式：

- 接受历史保留
- 或补一条 SQL / 脚本做回填

### 情况 D：真实上游行为异常

处理方式：

- 抓请求 ID
- 查日志与落库
- 与上游核对
- 必要时临时隐藏上游返回字段，避免影响用户信任

## 七、上线后验证模板

每次发布后，至少做这 4 步：

1. `curl` 打线上真实接口，拿到 `x-oneapi-request-id`
2. 用 `request_id` 查库，看新日志是否符合预期
3. 打开无痕窗口验证页面
4. 对照“新请求”和“历史记录”，避免把历史数据误判为缓存

## 八、结论

这个项目“老像有缓存问题”，本质上通常不是单一缓存，而是下面几类问题混在一起：

- 前端静态资源缓存
- CDN / 边缘节点缓存
- Go 进程内存配置未收敛
- 多实例发布窗口期
- 历史落库数据不会自动回填

以后遇到“没生效”，不要先问“是不是缓存”。
先问：

1. 新请求是否正确？
2. 数据库新记录是否正确？
3. 页面是不是旧资源？
4. 看的到底是实时值还是历史值？

按这个顺序查，基本不会再误判。
